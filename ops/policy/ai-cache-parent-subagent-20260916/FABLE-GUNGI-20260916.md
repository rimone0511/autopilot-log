## 0. 裁定の要約（一画面）

1. **目的の置き直し**: 本案件の目的は「キャッシュ最適化」ではない。**「Fable 5.1 を親として一日単位で走らせ続け、子（Astra/Sol/Terra/Luna・Claude子）を使いながら、本人が離席や圧縮を管理せず、サブスク枠の中で仕事量を最大化する」**こと。キャッシュ TTL・200K・40分はすべて**手段**であり評価軸ではない。
2. **最大のレバーは TTL ではなく「親に入る情報量」**。Codex 子は別ベンダーで親とキャッシュを一切共有しない。Claude 組み込み子も初回は親キャッシュを読まない。したがって親の消費を決めるのは「子から親へ返す差分報告の短さ」と「親履歴の圧縮タイミング」であり、子側 TTL 設定は二次的。R3 §D（差分報告）を**第一層**へ昇格させる。
3. **40分・温かい圧縮の価値を「節約」から「圧縮タイミングの制御」へ読み替える**。API単価（読み 0.025×）でのみ成り立つ節約論はサブスク枠では **UNVERIFIED**。一方「安全な区切りで、引継ぎを保存してから、製品の自動圧縮に先回りして一度だけ圧縮する」価値は枠計測の結果に依存しない。温かさは**おまけ**として位置づける。
4. **判定は外・実行は中・引継ぎは常時**。アイドル判定をモデル呼び出しで行うと（cron で「暇なら圧縮せよ」と投げる等）それ自体が空打ち延命と同じコストになる。判定は hook が書いたタイムスタンプを OS 側の通常スケジューラーが読む。モデル呼び出しは圧縮の**一回**だけ。引継ぎファイルは作業中に常時更新し、圧縮も失効も「引継ぎから戻れる」を前提にする。
5. **親の起動形態が未確認のまま経路を語れない**。対話TUI か、`-p --resume` を回すハーネスか、Agent SDK か、Desktop か。**これが設計書の第一の決定事項**。TUI なら外部から同一セッションへ圧縮を起こす確実な経路は現時点で見当たらず、**P4（遅延判断：休止時は何もせず、再開時に引継ぎから戻るか続けるかを決める）**が基線になる。
6. **`~/.claude/agents/` は両ホストとも不在（OBSERVED）**。R3 の「個別エージェントに `experimental.cacheTtl: "1h"`」は、まず**どの子をカスタムエージェントとして定義するか**を決めないと差分の置き場がない。
7. **0.025× を Max プラン枠の倍率として扱わない**。設計書中の数式は API 単価比較としてのみ許し、サブスク枠への言及は必ず「観測できたら」「UNVERIFIED」を付す。

- 検証: 圧縮の**開始と完了**、前後のアクティブ文脈量。まず低い仮閾値で機構を確認し、200K 近辺で1回。閾値を下げるほど得と考えず、再取得・再作業を含めて評価。

### T3 二重ゲート層（親の休止前一回圧縮。本人希望を実現する層）

**価値の定義（読み替え）**: 「製品の自動圧縮が作業中の悪いタイミングで発火する前に、安全な区切りで、引継ぎを保存済みの状態で、**一度だけ**圧縮する」。温かいキャッシュで読める（=API 単価なら 0.025×）のは**おまけ**であり、サブスク枠での効果は Test 0 の結果次第。

**ゲート（すべて成立で有効化。1つでも不成立なら P4 基線のまま）**:

| ゲート | 内容 | 不成立時 |
|---|---|---|
| G1 経路 | 親の起動形態（T0）に対応する「同一親セッションへ実際のモデル呼び出し／正式圧縮を起こす経路」が試験セッションで**1回**実証されている | P4 |
| G2 外判定 | アイドル判定（A・B）が hook の書いたタイムスタンプ＋OS 側通常スケジューラーで行われ、**非アイドル時にはモデル呼び出しが一切起きない**ことが実証されている | P4（cron 型「暇なら圧縮せよ」プロンプトは F2 の罠） |
| G3 一回性 | 発火が一回で止まり、圧縮後に再発火・延命ループがないこと。活動再開で予約が取り消されること | P4 |
| G4 温度確認 | 発火時点で A を再計算し、失効推定なら**圧縮しない**（冷たい圧縮を温かいと偽装しない）。その場合は P4 へ | P4 |
| G5 サイズ閾値 | 親コンテキストが縮める価値のある規模（設計書で数値候補。例: 窓の一定割合）を超えている。小さければ圧縮を省く | 圧縮省略 |

**P4 基線（遅延判断）**: 休止中は何もしない。再開時に SessionStart（resume）の `prompt_cache_likely_expired` / `seconds_since_last_response` を読み、(i) 失効前なら続行、(ii) 失効後は「そのまま続ける（冷たい再書込み1回）」か「引継ぎから新セッションで戻る」かを**規則で**決める（本人に選ばせない）。規則の候補は設計書で定める（例: 休止 X 時間超・親サイズ Y 超なら引継ぎ再開）。

**時計の定義（BRIEF §8 の A/B を観測源まで落とす）**:
- A（最終キャッシュ接触）: 本来は「最後にプレフィックスを読み書きしたリクエストの**開始**時刻」。観測できる近似は **Stop hook 時刻（最終応答終了）**。これは真の A より**遅い**ため「温かい」側に楽観的な推定になる。安全側に扱うには「最終リクエストの継続時間 < 余裕（60−40=20分）」を前提とし、長い最終ターン（例: 15分超）だったときは G4 で保守的に扱う。**推定であることを明示。**
- B（実活動）: UserPromptSubmit（本人入力）／認可済み作業の意味ある進捗。空の延命通知・キュー登録・子の活動だけでは B を更新しない。
- 発火条件: `now − A_est ≥ 40分` かつ `B に新規なし` かつ 親が推論中・ツール中・圧縮中でない かつ G4/G5 成立。
- 40分の根拠: TTL 60分 − 最終ターン所要 − スケジューラーのジッター − 圧縮所要の余裕。**固定値ではなく導出値**として設計書に書く。

**状態別処理**（BRIEF §8 の5状態を採用。設計書は状態遷移図にする）:
作業中（割り込まない） → 子待ち（機械集約→意味ある確認→親だけ圧縮して待つ案と比較；無限延命しない） → 休止可能（G1–G5 → 引継ぎ保存 → 一回圧縮） → 圧縮後（休止。再圧縮・延命なし。本人再開／認可済み結果で復帰） → 失効・不明（偽装しない。P4）。

## 付記: 本人向け一画面（平易・本人が判断する部分だけ）

今回は「方向決め」だけで、何も設定していません。
おすすめの順番は、(1) 子から親へ返す報告を短く固定する、(2) 親が作業の区切りごとに引継ぎメモを自動で残す、(3) その上で、待ちが長い子だけ1時間キャッシュ・Codex 子は約20万トークンで圧縮を**小さく試す**、(4) 「40分あいたら一度だけ圧縮」は、親をどう起動しているか（画面で対話しているか、プログラムが回しているか）で実現できるかが決まるので、まずそこを確認します。実現できない場合でも、引継ぎメモから戻れる形にするので、離席時間を気にする必要はありません。
本人に決めてもらいたいのは1点だけ: **親 Fable を普段どう起動しているか**（ターミナルで直接／何かのプログラム経由／Desktop）。
